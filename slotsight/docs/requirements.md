# SlotSight: Smart Parking Occupancy Counter

## 1. Project Overview

In small and crowded parking lots, people often have difficulty knowing which slots are free in real time. This can waste a lot of time and create traffic jams in the parking lot, increasing inconvenience and unhappiness. My proposed product, SlotSight, is a smart parking occupancy counter that uses a camera-based system to classify each defined parking slot as occupied or vacant, and shows live availability on a dashboard accessible online. SlotSight covers one fixed-camera parking lot in daytime and evening conditions, showing slot-level status while excluding payments, reservations, or license plate recognition.

## 2. Context and Starting Conditions

The development timeline of 2 weeks means that we have to make certain tradeoffs in our starting conditions, such as focusing on implementing features instead of optimizing for performance.

|                     | **Starting Conditions**                                                                                                                 | **Limitations**                                                                                                                                                                                                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Methods**         | Pretrained object detection (YOLO) to find vehicles, then a polygon-overlap check against predefined slots to decide occupied or vacant | Pretrained detectors can miss partially hidden, distant, or unusual vehicles (motorcycles, tricycles, vans). The overlap threshold needs tuning per camera angle. The method judges slots by vehicle position, so a car parked across two slots can be misclassified.                                            |
| **Software**        | Python, PyTorch/Ultralytics YOLO, OpenCV, a lightweight dashboard (Streamlit or Flask)                                                  | Limited to free, open-source tools. The dashboard is a prototype with no user accounts, security hardening, or scaling. Model licensing (for example, Ultralytics' license terms) should be checked if the work is ever commercialized.                                                                          |
| **Datasets**        | Own recorded footage of one lot (about 1 to 2 hours across different times of day), optionally a public set such as PKLot               | Little footage means limited variety in weather, lighting, and vehicle types, so results may not generalize beyond this lot. Hand-labeling ground truth is slow, which caps the size of the test set. Public datasets use different camera angles and regions, so they may not transfer well.                    |
| **Hardware**        | Smartphone camera (1080p, 30 fps) on a tripod or elevated mount, or an ESP32-CAM                                                        | A single phone viewpoint can't see every slot, and distant slots appear small and low in resolution. Phone battery, overheating, and storage limit recording length. An ESP32-CAM has low resolution and can't run the detector, so it could only stream or capture frames.                                      |
| **Data Processing** | Student laptop, CPU-only or with a modest GPU (for example, 4 GB VRAM), 16 GB RAM                                                       | Limited GPU memory restricts model size and frame rate. CPU-only inference may be too slow for real-time updates, so the system may need to process every Nth frame. The laptop is not suitable for continuous unattended deployment.                                                                            |
| **Coverage**        | One camera, about 10 to 30 slots visible, one lot                                                                                       | Results apply only to this lot and camera view. Slots hidden by pillars, trees, or large vehicles cannot be assessed. Multi-camera stitching and larger lots are out of scope.                                                                                                                                   |
| **Image Quality**   | 1080p video, fixed viewpoint, variable lighting (daylight, evening, rain), possible shadows and glare                                   | Night, heavy rain, glare, and long shadows reduce detection accuracy. Raindrops or fog on the lens can degrade the image. Camera shake or movement from wind or bumps can shift slot polygons. Controlled testing of weather is not possible, so only conditions that occur during the project can be evaluated. |
| **Storage**         | About 50 GB free for raw video, labeled frames, and logs                                                                                | logs Raw 1080p video fills storage quickly, so footage must be trimmed or deleted. Long-term retention of raw video is limited, which restricts re-running experiments on old data.                                                                                                                              |

## 3. Needs Assessment

| **Item**               | **Response**                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Stakeholders**       | Parking operator monitors the lot, drivers use availability info, and parking admin decides on signage or staffing |
| **Task and Decision**  | Know how many slots are free and where, then direct drivers or decide when the lot is full                         |
| **Object or Data**     | Parking slots and vehicles at the parking lot, viewed from a certain camera position                               |
| **Working Conditions** | Daylight to evening, rain, shadows, partial occlusion by large vehicles                                            |
| **Current Method**     | Manual walk-through, guard counting, or driving around                                                             |
| **Pain Point**         | Driver has difficulty knowing free slots under peak hours or rain, resulting in delays or congestion               |
| **Consequences**       | Queues, drivers circling, turned-away visitors, wasted staff time                                                  |
| **Evidence**           | The problem is currently being experienced personally, and through informal interviews with friends and family     |
| **User Need**          | Know current slot availability accurately enough to direct drivers without manual checking                         |

## 4. Product Definition and Scope

The product is a vision-based occupancy monitor that gives the user a live per-slot and total free-slot view for one lot.

**Included**: slot definition, occupancy classification, dashboard, and logging. \
**Excluded**: payments, reservations, plate reading, and multi-camera stitching. \
**Risks that could change scope**:camera angle limiting slot visibility, permission to record, and night performance.

## 5. Product Requirements Document (PRD)

| **ID/Area**                  | **Product Requirement**                                                                         | **Source / Rationale**                                                                                                   | **Acceptance Criterion**                                                            | **Evidence Method**                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **R-01 (Functions)**         | The system must classify each defined slot as occupied or vacant from camera frames.            | The system needs to know availability without manual checks.                                                             | Per-slot accuracy >= 90% on the reference test set.                                 | Compare outputs with hand-labeled ground truth.                                                      |
| **R-02 (Functions)**         | The system must report the total number of free slots for the lot.                              | Operator decides when the lot is full.                                                                                   | Reported count matches the ground-truth count in >= 90% of test frames.             | Compare with labeled frames.                                                                         |
| **R-03 (Data / Interfaces)** | The system must accept a recorded video file or live stream plus a slot-polygon configuration.  | Hardware constraints may limit video streaming in some use cases.                                                        | Given a video and config, the system produces timestamped slot statuses.            | Inspection of the output, given the input file with known parking statistics.                        |
| **R-04 (Performance)**       | Status must update at least every five seconds.                                                 | Availability must be seen in near real-time to assess availability changes.                                              | Measured update interval <= 5 seconds.                                              | Timing test on the target hardware.                                                                  |
| **R-05 (Performance)**       | Accuracy under evening and rainy conditions must not fall below 90% of the daytime result.      | Working conditions in the above sections require use in both daytime and evening conditions, in a wide range of weather. | Per-condition accuracy is reported and meets the threshold.                         | Run labeled test sets per condition (daytime, evening, rainy, etc.).                                 |
| **R-06 (User Interaction)**  | The dashboard must show each slot's status on a lot map with the time of last update.           | The operator needs a quick, trustworthy view.                                                                            | In the demo, all slots appear with status and timestamp.                            | Workflow demonstration, with pinpointable UI elements showing the timestamp and status of each slot. |
| **R-07 (User Interaction)**  | Slots that the model cannot classify confidently must display as "unknown" rather than a guess. | Wrong "free" readings send drivers to occupied slots.                                                                    | Low-confidence cases in the test set display as unknown.                            | Test with partly occluded cases.                                                                     |
| **R-08 (Data)**              | The system must be able to export occupancy history as either a CSV or Excel file.              | Supports analysis of peak times and the time that each vehicle stays at the parking lot.                                 | The exported file contains slot ID, status, and timestamp for all processed frames. | Inspection of the exported file.                                                                     |
